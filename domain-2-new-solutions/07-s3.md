# Amazon S3

> **Object storage at internet scale. 11×9s durability, virtually unlimited storage, the canonical AWS data lake and backup target. Foundation of countless AWS services.**

Maps to: **Domain 2.5 — Design high-performance architectures** (storage selection)

---

## Overview

- **Object storage** (not block, not file) — flat namespace within a bucket
- **Object size**: 0 B to **5 TB** per object
- **Single PUT limit**: 5 GB; use **multipart upload** for objects > 100 MB (required > 5 GB)
- **11×9s durability** (99.999999999%) for Standard / IA / Glacier classes
- **99.99% availability** (Standard); varies by class
- **Strong read-after-write consistency** for **all** operations (PUT, overwrite, DELETE). There is no eventual consistency window anymore.
- **10,000 buckets per account** by default (raisable to 1 million via service quota)
- Buckets are **Region-scoped**; bucket names are globally unique across all AWS accounts
- Use cases: backups, data lake, static assets, big data analytics, CDN origin, ML training data, archives

## Storage Classes

| Class                                                  | Use case                            | Min duration | Min object size                  | Retrieval cost       | Availability      |
| ------------------------------------------------------ | ----------------------------------- | ------------ | -------------------------------- | -------------------- | ----------------- |
| **S3 Standard**                                        | Frequent access                     | None         | None                             | None                 | 99.99%            |
| **S3 Intelligent-Tiering**                             | Unknown / changing patterns         | None         | 128 KB (below = always Frequent) | None                 | 99.9%             |
| **S3 Standard-IA**                                     | Infrequent but rapid access         | 30 days      | 128 KB                           | Per-GB retrieval     | 99.9%             |
| **S3 One Zone-IA**                                     | Re-creatable, infrequent            | 30 days      | 128 KB                           | Per-GB retrieval     | 99.5% (single AZ) |
| **S3 Glacier Instant Retrieval**                       | Archive with ms retrieval           | 90 days      | 128 KB                           | Per-GB retrieval     | 99.9%             |
| **S3 Glacier Flexible Retrieval** (formerly "Glacier") | Archive, retrieval in minutes/hours | 90 days      | 40 KB                            | Per-GB + per-request | 99.99%            |
| **S3 Glacier Deep Archive**                            | Long-term archive (7-10 yrs)        | 180 days     | 40 KB                            | Per-GB + per-request | 99.99%            |
| **S3 Express One Zone**                                | Single-digit ms latency, single AZ  | None         | None                             | None                 | Single-AZ         |
| **S3 on Outposts**                                     | On-prem object storage              | None         | —                                | —                    | Single-site       |

### Glacier Retrieval Tiers (Flexible Retrieval)

- **Expedited** — 1-5 minutes (most expensive)
- **Standard** — 3-5 hours (default)
- **Bulk** — 5-12 hours (cheapest, often free for Deep Archive bulk)

### S3 Express One Zone

- **Directory bucket** type (not general purpose) — flat namespace optimized for high IOPS
- **Single-digit millisecond first-byte latency** (10× faster than Standard)
- Stored in a **single AZ** (you choose); no cross-AZ redundancy
- Use for: high-frequency access workloads (ML training data shuffling, analytics, media)
- Object size up to 5 TB
- No SSE-KMS, no replication (yet), no S3 Object Lock, no public-access ACL

## S3 Intelligent-Tiering

Moves objects automatically between access tiers based on usage patterns.

- **Frequent Access tier** — default; objects begin here
- **Infrequent Access tier** — after **30 days** without access
- **Archive Instant Access tier** — after **90 days** (ms retrieval)
- **Archive Access tier** (optional) — after 90 days, retrieval in minutes/hours
- **Deep Archive Access tier** (optional) — after 180 days, retrieval in 12 hours

**No retrieval fees**, but a **monitoring & automation fee** per 1,000 objects (only for objects > 128 KB).

**Use when** access patterns are unknown or change frequently. Easy way to optimize cost without lifecycle policies.

---

## Lifecycle Policies

Automate transitions and expirations:

- **Transition actions** — move objects between classes (e.g., Standard → Standard-IA → Glacier → Deep Archive)
- **Expiration actions** — delete current or previous-version objects after N days
- Can apply to: entire bucket, prefix, or tag-based filter
- **Expire incomplete multipart uploads** — important for cost hygiene
- **Delete-marker cleanup** — remove orphan delete markers from versioned buckets

### Required minimum durations (gotcha)

- Standard-IA / One Zone-IA: minimum 30 days
- Glacier Instant / Flexible: minimum 90 days
- Deep Archive: minimum 180 days

## Versioning, MFA Delete, Object Lock

### Versioning

- Bucket-level setting
- Once **enabled** can be **suspended** but **not disabled** entirely
- Each PUT creates a new version with a unique version ID
- DELETE creates a **delete marker** (logical delete); reading the object returns 404 but versions remain
- Required for replication and Object Lock

### MFA Delete

- Requires MFA to permanently delete a version or change versioning state
- Can ONLY be enabled by the **root user** via CLI / API (not console)
- Recommended for highly-regulated buckets

### S3 Object Lock (WORM)

- **Write Once, Read Many** — prevents object deletion or modification
- **Versioning must be enabled** before enabling Object Lock
- Two retention modes:
  - **Governance mode** — users with `s3:BypassGovernanceRetention` can remove
  - **Compliance mode** — **no one** (including root) can remove until retention expires; immutable
- **Legal Hold** — independent of retention period; can be applied/removed by users with `s3:PutObjectLegalHold`
- Common pattern for compliance: SEC Rule 17a-4, HIPAA, SOX, financial archives

## Replication (SRR + CRR)

### Same-Region Replication (SRR)

- Replicate between buckets in the **same Region**
- Use cases: log aggregation, production-to-test sync, sovereignty within Region

### Cross-Region Replication (CRR)

- Replicate to a bucket in a **different Region**
- Use cases: DR, compliance, latency reduction for distributed users

### Common requirements

- **Versioning must be enabled** on source and destination
- **IAM role** for replication
- Async replication; default not retroactive (existing objects)
- **NOT transitive** — A → B and B → C does not mean A → C
- **SSE-C encrypted objects are NOT replicated**

### Replication Time Control (RTC)

- **Replicate 99.99% of objects within 15 minutes** (backed by SLA)
- Replication metrics + S3 Events for monitoring
- Use for compliance scenarios requiring guaranteed replication latency

### Batch Replication

- Replicate **existing objects** (replication is not retroactive by default)
- One-time job that processes existing inventory

### Bidirectional / Two-Way Replication

- Set up replication rules from A → B AND B → A
- Supports active-active scenarios

### Delete behavior

- Configurable: replicate delete markers (default off)
- Permanent deletes by version ID are not replicated

## S3 Encryption

### Server-Side Encryption (SSE)

| Type         | Key management                         | Default?                                       | Use case                                                                    |
| ------------ | -------------------------------------- | ---------------------------------------------- | --------------------------------------------------------------------------- |
| **SSE-S3**   | AWS-managed keys (AES-256)             | **Default for all new objects**                | Most general use                                                            |
| **SSE-KMS**  | AWS KMS keys (customer or AWS-managed) | Opt-in                                         | Audit / rotation / centralized key control                                  |
| **DSSE-KMS** | KMS, **dual-layer** encryption         | Opt-in                                         | Compliance requiring two independent encryption layers (e.g., FedRAMP High) |
| **SSE-C**    | Customer-provided key on every request | Opt-in                                         | Customer holds keys exclusively (HMAC stored for validation)                |

### Client-Side Encryption (CSE)

- **CSE-KMS** — encrypt with KMS data keys before upload
- **CSE-C** — fully customer-managed; HTTPS required; AWS sees only ciphertext

### S3 Bucket Keys (cost optimization for SSE-KMS)

- Reduces KMS API calls by ~99% by caching a bucket-level data key
- Significant cost savings when many objects are SSE-KMS encrypted
- **Enabled per-bucket**; works seamlessly with KMS

### Forcing encryption

Bucket policy denying uploads without encryption header:

```json
{
  "Effect": "Deny",
  "Action": "s3:PutObject",
  "Condition": {
    "StringNotEquals": { "s3:x-amz-server-side-encryption": "aws:kms" }
  }
}
```

### Forcing TLS / HTTPS

```json
{
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Condition": { "Bool": { "aws:SecureTransport": "false" } }
}
```

## Security Defaults

- **Block Public Access (BPA)** is **enabled by default** on new buckets
- **ACLs are disabled by default** on new buckets (Object Ownership = Bucket owner enforced)
- **SSE-S3 encryption applied by default** to all new objects
- These defaults are huge wins for security posture — old notes assuming public-by-default are outdated

## Access Controls (in order of preference)

### IAM policies (identity-based)

- Use for IAM users / roles in the same account
- Standard IAM `s3:*` actions

### Bucket policies (resource-based)

- Attached to the bucket; defines who can access what
- **Size limit: 20 KB** per bucket policy
- Supports cross-account access without IAM role chaining
- Required for public access (with BPA disabled)

### S3 Access Points

- Named endpoints per use case; each has its own access policy
- One bucket can have multiple access points (e.g., `analytics-readonly`, `ingest-writeonly`)
- Optional VPC restriction (private-only access points)
- Useful when many apps need different scopes against the same bucket
- Each access point gets a unique hostname

### S3 Multi-Region Access Points (MRAP)

- **Global endpoint** that routes requests to the closest replicated bucket
- Active-active or active-passive routing via Route 53-style health checks
- Use case: globally distributed users, automatic failover between Regions
- Works with replicated buckets across multiple Regions

### S3 Access Grants

- **IAM Identity Center-based** fine-grained access to S3
- Map **users / groups / IAM principals to S3 prefixes** with specific permissions
- Eliminates need to bake user-specific IAM policies; scales to thousands of users
- **Per-user audit** in CloudTrail (shows actual user, not shared role)
- Integrates with Trusted Identity Propagation for analytics workloads (Athena, Redshift, EMR)

### S3 ACLs (legacy)

- Object-level or bucket-level lists of permitted principals
- **Disabled by default on new buckets** (use bucket policies + IAM instead)
- Still required for some niche scenarios (e.g., CloudFront log buckets)

## VPC Endpoints for S3

### Gateway Endpoint (free)

- Added as a route table entry (prefix list `pl-xxxxx`)
- **Free**; no data processing charges
- Only accessible from within the VPC — **cannot be reached from VPN / DX / peered VPC / TGW**
- One per VPC per service

### Interface Endpoint (PrivateLink)

- ENI with private IP in your subnet
- **Paid** (per hour + per GB)
- Accessible from on-prem via VPN / DX, from peered VPCs / TGW
- Use when you need cross-VPC or hybrid private access to S3

## S3 Object Lambda

- Transform data **on the fly** as it's retrieved from S3 — no separate copy needed
- Set up: S3 bucket + Access Point + **Object Lambda Access Point** + Lambda function
- Lambda receives object, transforms it, returns transformed bytes to caller
- Use cases:
  - PII redaction
  - Format conversion (XML → JSON, CSV → Parquet)
  - Image resize / watermarking
  - Data enrichment from external APIs
  - Custom auth checks per request

---

## Static Website Hosting

- Bucket can serve as a static website (HTML, CSS, JS, images)
- Endpoint: `<bucket>.s3-website-<region>.amazonaws.com`
- **HTTPS NOT supported** on the S3 website endpoint directly
- For HTTPS: put **CloudFront in front** of S3 (with OAC) — also gives custom domain support
- Configure: index document, error document, redirect rules
- Use bucket policy to allow public read

## CloudFront + S3

### Origin Access Control (OAC) — recommended

- **Replaces** the legacy Origin Access Identity (OAI)
- Restricts S3 bucket to only allow access from a specific CloudFront distribution
- Supports SSE-KMS encrypted buckets (OAI did not)
- Supports all AWS Regions (OAI had gaps)
- **OAC is the modern answer**; if you see OAI in a question, it's the legacy option

### S3 vs CloudFront + S3 vs CloudFront + Transfer Acceleration

- **S3 alone**: simple, regional, no edge caching
- **CloudFront + S3**: global edge caching, lower latency for reads, HTTPS, custom domain
- **S3 Transfer Acceleration**: edge upload acceleration via CloudFront network (uploads only — for downloads use CloudFront)

---

## S3 Mountpoint & S3 CSI

### Mountpoint for Amazon S3

- **File-system style** access to S3 from Linux (FUSE-based)
- High-throughput sequential reads / writes
- NOT a full POSIX filesystem — no atomic rename, no random write in the middle of a file
- Best for: ML training pipelines, genomics, media processing where you need file-like access on S3 data

### Mountpoint S3 CSI Driver for EKS

- Mount S3 buckets as volumes in Kubernetes pods
- Same constraints as Mountpoint

## Performance

### Request rates per prefix

- **3,500 PUT / COPY / POST / DELETE per second per prefix**
- **5,500 GET / HEAD per second per prefix**
- No prefix limit — partition by adding more prefixes for higher aggregate throughput
- Example: 10 prefixes → 55,000 GET/sec aggregate

### Multipart Upload

- Required for objects > 5 GB; recommended > 100 MB
- Parts can be uploaded in **parallel** for higher throughput
- Failed uploads can resume from last successful part
- Set lifecycle policy to expire **incomplete multipart uploads** (cost hygiene)

### Transfer Acceleration

- Uploads via the nearest **CloudFront edge** location, then over AWS backbone to the bucket
- Best for cross-Region uploads of large files
- Pay per GB transferred; only enable if it gives measurable speedup (use AWS speed comparison tool)

### Byte-Range Fetches

- Parallelize downloads by requesting different byte ranges of the same object
- Use for large files

## Event Notifications

Trigger downstream processing when bucket events occur.

### Supported targets

- **Amazon SNS**
- **Amazon SQS**
- **AWS Lambda**
- **Amazon EventBridge** (recommended for new designs; richer filtering, more targets)

### Event types

- `s3:ObjectCreated:*` (Put, Post, Copy, CompleteMultipartUpload)
- `s3:ObjectRemoved:*` (Delete, DeleteMarkerCreated)
- `s3:ObjectRestore:*` (Glacier restore lifecycle)
- `s3:Replication:*`
- `s3:LifecycleExpiration:*`
- `s3:LifecycleTransition`
- `s3:IntelligentTiering`
- `s3:ObjectTagging:*`
- `s3:ObjectAcl:Put`

> 💡 **Exam pattern**: "fan out S3 events to multiple targets with filtering" → **EventBridge** (vs SNS/SQS/Lambda which are one-target-each per event).

## Inventory, Storage Lens, Analytics

### S3 Inventory

- Daily / weekly CSV / ORC / Parquet manifest of objects in a bucket
- Includes object metadata (size, last modified, storage class, encryption, replication, lock status)
- Use for: large-scale audits, Batch Operations input

### S3 Storage Lens

- Organization-wide visibility into S3 usage and activity
- Anomaly detection, recommendations
- Default dashboard (free) + Advanced metrics (paid)
- Export to S3 as CSV / Parquet; publish to CloudWatch
- Aggregates by account, Region, bucket, prefix

### S3 Analytics — Storage Class Analysis

- Recommends when to transition objects from Standard to Standard-IA
- Does NOT work for One Zone-IA or Glacier classes
- Daily reports; 24-48h lag

### S3 Batch Operations

- Execute large-scale operations on billions of objects: COPY, RESTORE, REPLACE TAGS, INVOKE LAMBDA
- Driven by S3 Inventory manifest or CSV input
- Use cases: bulk encrypt existing objects, bulk replicate, bulk metadata change

### S3 Select / Glacier Select

- Query subset of an object with SQL-like syntax (CSV, JSON, Parquet)
- Reduces data transfer and processing time
- Note: deprecation timeline announced — prefer Athena for new use cases

## Requester Pays

- Requester (not bucket owner) pays for **data transfer and requests**
- Bucket owner still pays for storage
- Use case: bucket owner sharing large datasets without bearing transfer costs (e.g., public scientific data with controlled access)
- Requester must include `x-amz-request-payer` header

## Pricing Dimensions

- **Storage** — per GB/month (varies by class)
- **Requests** — per 1,000 requests (varies by request type)
- **Data transfer**:
  - **Inbound to S3**: FREE
  - **Same Region to EC2**: FREE
  - **To CloudFront**: FREE
  - **To other Regions / internet**: paid per GB
- **Management features** — Storage Lens advanced, Inventory, Analytics, Object Lambda
- **Replication** — per-GB charges for replicated data + cross-Region transfer
- **Transfer Acceleration** — per-GB premium
- **Intelligent-Tiering monitoring** — per-1,000-object fee

## S3 Tables

- **Fully managed Apache Iceberg tables** stored in S3
- Optimized for analytics: ~3× query performance, ~10× transactions/sec vs self-managed Iceberg
- Automatic compaction, snapshot management, and metadata maintenance
- Integrates with Athena, Redshift, EMR, Glue, Spark
- Use case: data lakehouse on S3 without managing Iceberg metadata yourself

---

## S3 Vectors

- Store and query vector embeddings natively in S3
- Up to **1 billion vectors per index**
- ~100 ms query latency
- ~90% cheaper than dedicated vector databases for non-real-time workloads
- Native S3 security (IAM, encryption, BPA)
- Use case: cost-effective vector storage for RAG / semantic search where sub-50ms latency isn't required

---

## Trusted Identity Propagation Integration

- S3 Access Grants + IAM Identity Center propagates **user identity** to S3 queries via Athena / Redshift / EMR / QuickSight
- CloudTrail captures actual user identity (not a shared role)
- Foundation for per-user audit in analytics workflows

## Cross-Account Access Patterns

1. **Bucket policy + IAM in caller account** — simplest, no role assumption
2. **Cross-account IAM role** — caller assumes a role in target account
3. **S3 Access Points with cross-account policies**
4. **S3 Access Grants** (modern, scales to thousands of users)
5. **ACL + IAM** (legacy, avoid)

- JSON config on the bucket
- Up to 100 rules per bucket
- Methods: GET, PUT, POST, DELETE, HEAD
- Configure: `AllowedOrigin`, `AllowedHeader`, `AllowedMethod`, `MaxAgeSeconds`, `ExposeHeader`

## Monitoring & Auditing

- **CloudTrail data events** — log every object-level GET/PUT/DELETE (paid)
- **CloudTrail management events** — bucket-level config changes (free)
- **S3 Server Access Logging** — request-level log to another S3 bucket (best-effort, same-Region target, no charge)
- **CloudWatch metrics** — request counts, latencies, errors, bucket size
- **AWS Config** — track bucket configuration changes; conformance pack checks
- **Macie** — discover and classify PII in S3 (ML-based)
- **Storage Lens** — usage and activity dashboards

## Bucket Naming Rules

- 3-63 characters
- Lowercase letters, numbers, hyphens, periods
- Must start with letter or number
- Must NOT be formatted as an IP address (e.g., `192.168.0.1`)
- **Globally unique** across all AWS accounts (Region-scoped buckets, but namespace is global)
- Avoid periods for HTTPS scenarios (cert SAN issues)

## Exam Tips

- **Strong consistency** — all operations (PUT, overwrite, DELETE) are strongly consistent;
- **1mln buckets default per account**
- **SSE-S3 is default encryption**
- **Block Public Access default ON**
- **ACLs disabled by default** use bucket policies + IAM
- **S3 Express One Zone** for high-IOPS, single-digit-ms latency single-AZ workloads (ML training, analytics)
- **DSSE-KMS** for dual-layer encryption (FedRAMP High, top-tier compliance)
- **S3 Bucket Keys** to reduce KMS API costs ~99% on heavily-encrypted buckets
- **OAC (Origin Access Control)** replaces OAI for CloudFront → S3
- **MRAP** for global active-active S3 with automatic failover
- **S3 Access Grants** = IAM Identity Center-based per-user access at scale
- **EventBridge** is preferred over SNS/SQS/Lambda direct for S3 events (better filtering, more targets)
- **Replication Time Control (RTC)** = 99.99% replicated within **15 minutes** (with SLA)
- **Batch Replication** to replicate existing objects (default replication is not retroactive)
- **Object Lock Compliance mode** = immutable even for root; **Governance mode** = bypassable with permission
- **Versioning required** for replication and Object Lock
- **MFA Delete** only enabled via CLI by root user
- **Glacier Instant Retrieval** = ms retrieval at archive prices (90-day minimum)
- **Glacier Flexible Retrieval** has 3 tiers: Expedited (1-5 min), Standard (3-5 hr), Bulk (5-12 hr)
- **Deep Archive Bulk retrievals are often free** (cheapest archive option)
- **Transfer Acceleration** is for uploads via CloudFront edge; for downloads use CloudFront directly
- **Mountpoint for S3** = file-system view of S3 (Linux/EKS) — high-throughput sequential I/O, not full POSIX
- **S3 Tables** (Apache Iceberg) for managed lakehouse on S3
- **S3 Vectors** for cost-effective vector storage when sub-50ms latency isn't required

## Exam Traps

- Gateway Endpoints are **VPC-only** — they cannot be reached from on-prem (VPN/DX). Use Interface Endpoints (PrivateLink) instead
- S3 static website endpoint is **HTTP only** — place CloudFront in front for HTTPS
- Cross-Region Replication is **not transitive** — A → B and B → C does not replicate A → C; configure each path explicitly
- CRR only applies to **new objects** by default — use Batch Replication for existing objects
- **SSE-C objects cannot be replicated** cross-region — AWS never stores the customer-provided key
- **OAC** (Origin Access Control) is the current recommendation — OAI is legacy
- Object Lock **requires versioning** — it cannot be enabled on an unversioned bucket
- Compliance mode retention **cannot be shortened by anyone**, including root — only extension is allowed (Governance mode allows override with special permissions)
- MFA Delete can only be enabled via **CLI/API by the root user** — the console does not support it
- Bucket policy max size is **20 KB**, not 100 KB — for more granular access use Access Points (each AP has its own policy)
- S3 Standard-IA has a **30-day minimum duration** charge — deleting earlier still incurs the full 30-day cost
- Glacier Flexible Retrieval is the **renamed original "Glacier"** tier — not a new class
- S3 Tables are **managed Apache Iceberg tables** for analytics — unrelated to DynamoDB
- S3 Express One Zone is **single-AZ by design** — durable but not HA across AZs; no replication or Object Lock support
- Intelligent-Tiering monitoring fee applies only to objects **> 128 KB** — smaller objects stay in Frequent Access tier
- EventBridge integration is **opt-in per bucket** — S3 Event Notifications must be configured to route to EventBridge; it does not happen automatically
- S3 Access Grants is a **layer on top of IAM** for user-prefix mapping — it does not replace IAM
- Glacier Vault Lock and Object Lock are **different features** — Vault Lock is for the legacy Glacier vault API; Object Lock is for S3 buckets
- S3 buckets are **Region-fixed** — they cannot be moved; replicate to a new bucket in the target Region instead
- S3 static hosting does **not support custom HTTPS certificates** — use CloudFront with an ACM cert
