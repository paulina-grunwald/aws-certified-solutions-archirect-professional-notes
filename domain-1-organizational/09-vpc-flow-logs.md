# VPC Flow Logs

> **Capture IP traffic metadata going to and from network interfaces in your VPC.**

Maps to: **Domain 1.1 — Architect network connectivity strategies** (traffic inspection, observability)

---

## Overview

- VPC Flow Logs capture **metadata** about IP traffic going to/from network interfaces in a VPC
- Flow log data is stored in **CloudWatch Logs**, **S3**, or **Amazon Data Firehose** (formerly Kinesis Data Firehose)
- Flow Logs support resource tagging and **Tag-on-Creation** (apply tags automatically as flows are captured for consistent labeling)
- If you launch more instances into a subnet after creating its flow log, a new log stream (CloudWatch Logs) or log file object (S3) is created for each new network interface
- After you've created a flow log, **you cannot change its configuration** (e.g., cannot associate a different IAM role) — must delete and recreate

> 📌 **Deleting a flow log** does NOT delete any existing flow log records, log streams (CloudWatch Logs), or log file objects (S3) for a network interface.

## Flow Log Levels

Flow logs can be created at three levels:

- **VPC** — logs every ENI in the VPC
- **Subnet** — logs every ENI in the subnet
- **Network Interface (ENI)** — logs a single ENI

> 📌 It's possible to stream VPC Flow Logs from CloudWatch to AWS Lambda or Amazon OpenSearch Service (formerly Elasticsearch Service).

> 💡 **You can't enable flow logs for VPCs that are peered with your VPC unless the peer VPC is in your account.**

---

## Traffic NOT Captured

- Traffic from instances when they contact the **AWS DNS server**. If you use your own DNS server, all traffic to that server IS logged.
- Traffic generated by Windows instances for **Amazon Windows license activation**
- Traffic to and from **169.254.169.254** (instance metadata) and **169.254.169.123** (Amazon Time Sync Service)
- **DHCP traffic**
- Traffic to the reserved IP address from the default VPC router
- Traffic between a **VPC endpoint network interface** and a **Network Load Balancer** network interface

---

## Aggregation Interval

- Default maximum aggregation interval: **10 minutes**
- When creating a flow log, you can optionally specify a **1-minute** maximum aggregation interval
- ❗ **On Nitro-based instances, the aggregation interval is always 1 minute or less**, regardless of the specified maximum

## Flow Log Record Fields (V2–V8)

### Version 2 (default fields)

- **`srcaddr` / `dstaddr`** — source and destination IP addresses
- **`srcport` / `dstport`** — source and destination ports
- **`protocol`**, **`packets`**, **`bytes`**, **`start` / `end`**, **`log-status`**
- **`action`**: **`ACCEPT`** (allowed by SGs and NACLs) or **`REJECT`** (blocked)

### Version 3 (additional fields)

- **`vpc-id`**, **`subnet-id`**, **`instance-id`**
- **`tcp-flags`** — bitmask of TCP flags set during the aggregation interval
- **`type`** — IPv4, IPv6, or EFA
- **`pkt-srcaddr` / `pkt-dstaddr`** — original packet-level source/destination (different from `srcaddr`/`dstaddr` when traffic goes through NAT GW, NLB, or proxies)

### Version 4 (2020 — location fields)

- **`region`**, **`az-id`**, **`sublocation-type`**, **`sublocation-id`** — for Outposts / Local Zones / Wavelength workloads

### Version 5 (2021 — AWS service + path)

- **`pkt-src-aws-service` / `pkt-dst-aws-service`** — identifies AWS service (e.g., S3, EC2) at the packet endpoint
- **`flow-direction`** — `ingress` or `egress`
- **`traffic-path`** — the path egress traffic takes (IGW, NAT GW, VGW, VPC peering, TGW, Gateway Endpoint, etc.)

### Version 7 (May 2024 — ECS metadata)

- **`ecs-cluster-name`**, **`ecs-cluster-arn`**, **`ecs-service-name`**
- **`ecs-task-id`**, **`ecs-task-arn`**, **`ecs-task-definition-arn`**
- **`ecs-container-id`**, **`ecs-second-container-id`**, **`ecs-container-instance-id`**, **`ecs-container-instance-arn`**

### Version 8 (2025 — reject reason)

- **`reject-reason`** — explains **why** a packet was REJECTed (e.g., `BPA` for Block Public Access on internet gateways, `unknown` for other reject paths)
- Custom format auto-sets `version` to the highest field used — including `reject-reason` bumps records to V8
- Critical for triaging connectivity failures: lets you distinguish **SG / NACL drops** from **BPA drops** without packet captures

> 💡 **`pkt-srcaddr` vs `srcaddr`**: critical for NAT / NLB traffic — `srcaddr` shows the NAT/NLB ENI IP, `pkt-srcaddr` shows the originating client IP. Always use `pkt-*` fields when troubleshooting connectivity through NAT or NLB.

## Custom Format & Output Formats

### Custom format

- Select exactly which fields to include and their order
- **Required to capture any V3+ field** (default format = V2 fields only)
- Multiple flow logs per VPC are allowed — each can have its own format

### Output formats (S3 destination only)

- **Plain text** (default) — newline-delimited
- **Apache Parquet** — columnar; ~20% lower storage, up to 7× faster Athena queries, lower scan costs
- **Hive-compatible S3 prefixes** — partition by `aws-region=X/year=YYYY/month=MM/day=DD/hour=HH`
- **Hourly partitions** — separate prefix per hour for faster partition pruning

---

## Athena Integration

- VPC console has a built-in Athena integration: one click generates a CloudFormation template creating the Athena database, workgroup, and partitioned flow logs table
- Ships with **predefined queries** for top talkers, REJECTed traffic, traffic by port, traffic to/from a specific IP, traffic via NAT
- For Parquet + Hive partitions, use **partition projection** to skip `MSCK REPAIR TABLE`
- Combine with **QuickSight** for dashboards

---

## CloudWatch Contributor Insights

- Apply Contributor Insights rules on flow logs in CloudWatch Logs to surface **Top-N contributors**
- Common rules: top source IPs by REJECTed packets, top destinations by bytes, top ports by traffic
- No S3 / Athena needed; works directly on the log group
- Useful for fast security visibility and anomaly detection

---

## AWS Managed Interfaces — What You CAN Capture

- ELB / ALB / NLB target ENIs
- NAT Gateway ENIs
- Transit Gateway attachment ENIs (or use the dedicated **TGW Flow Logs** feature)
- RDS, ElastiCache, Redshift cluster ENIs
- Workspaces, AppStream ENIs
- VPC Interface Endpoint (PrivateLink) ENIs

> ⚠️ **Gateway Endpoints (S3, DynamoDB) have no ENI**, so flow logs do NOT capture them as endpoint traffic — only as egress through the prefix list in the route table.

---

## Status Values (`log-status` field)

- **`OK`** — data logged normally
- **`NODATA`** — no traffic to or from the ENI during the interval
- **`SKIPDATA`** — some records were skipped (missing IAM permissions, capacity issues, or internal errors)

---

## Transit Gateway Flow Logs

- Separate feature from VPC Flow Logs — captures traffic at the **TGW attachment** level
- Same destinations: CloudWatch Logs, S3, Amazon Data Firehose
- Same output options: plain text, Parquet, Hive partitioning
- Default + custom format available
- Use cases: troubleshoot inter-VPC connectivity via TGW, audit transit traffic, capture flows VPC Flow Logs wouldn't see (TGW-internal routing)

> 💡 When the scenario is **"centrally inspect traffic across many VPCs connected via TGW"**, the answer is often **TGW Flow Logs**, not per-VPC Flow Logs.

---

## VPC Flow Logs for ECS (Version 7, May 2024)

- New ECS metadata fields enrich flows from tasks running on EC2 or Fargate
- Enable via console checkbox or `IncludeECSMetadata` option in custom format
- Solves the "which task generated this flow?" problem for ephemeral Fargate tasks
- Use cases: container-level security analysis, microservices traffic mapping, multi-tenant isolation auditing

---

## Cross-Account / Centralized Logging

- Deliver flow logs from many accounts / VPCs to a **central S3 bucket** in a logging account
- Bucket policy in the central account grants `delivery.logs.amazonaws.com` write access; member accounts configure flow logs to write to that bucket ARN
- Combine with **AWS Organizations + SCP** to enforce flow logs on every VPC org-wide
- Combine with **S3 Object Lock** for immutable audit trail
- Query the centralized bucket with Athena from any account that has read access

## Exam Tips

- VPC Flow Logs capture **metadata only** (5-tuple, packets, bytes) — NOT packet payload; for payload use **Traffic Mirroring** or **Network Firewall** logging
- **3 destinations**: CloudWatch Logs, S3, Amazon Data Firehose — no direct SNS / SQS / EventBridge
- **3 levels**: VPC (logs every ENI in the VPC), Subnet, individual ENI
- For real-time alerting use **CloudWatch Logs subscription filters → Lambda / Kinesis**; the flow log itself has 1-min minimum aggregation latency
- For cost-effective long-term storage + ad-hoc querying use **S3 + Parquet + Athena**
- For dashboards use **Contributor Insights** (CloudWatch) or **QuickSight** (S3 + Athena)
- **`pkt-srcaddr` / `pkt-dstaddr`** show original endpoints when traffic flows through NAT GW, NLB, or proxies — critical for troubleshooting
- For **TGW central inspection** scenarios → consider **TGW Flow Logs**, a separate feature
- Flow Logs are enabled per-resource; use **SCPs + AWS Config rules** to enforce them org-wide
- **Default format = V2 fields only** — use custom format to capture V3+ fields (`vpc-id`, `instance-id`, `pkt-srcaddr`, ECS metadata, `reject-reason`, etc.)
- **V8 `reject-reason` (2025)** tells you WHY a packet was rejected (e.g., `BPA` for Block Public Access) — distinguish SG/NACL drops from BPA drops

## Exam Traps

- Flow Logs capture **metadata only** (no payload, no L7 data) — for packet contents, use Traffic Mirroring or Network Firewall with logging
- Flow Logs have a **1-minute minimum aggregation** interval — they are not real-time and are the wrong tool for sub-minute security automation
- Flow Logs **exclude certain traffic types**: Amazon DNS, `169.254.169.254` (instance metadata), `169.254.169.123` (Time Sync), DHCP, Windows license activation, and VPC Endpoint ENI-to-NLB ENI traffic
- Flow Logs are **immutable after creation** — to change configuration, you must delete and recreate
- Flow Logs are **per-Region** — a multi-Region setup requires Flow Logs in each Region
- Gateway Endpoints (S3, DynamoDB) have **no ENI** — Flow Logs only capture this traffic as egress via the prefix list, not as endpoint traffic
- Flow Logs capture **network metadata**; CloudTrail captures **API call history** — both are needed for a complete audit. They are different services
- Behind a NAT Gateway, use **`pkt-srcaddr`** for the originating instance IP — `srcaddr` shows only the NAT GW IP, which mis-attributes traffic
- For DNS query auditing, use **Route 53 Resolver Query Logs** — Flow Logs do not capture DNS query details
- Flow Logs on a peered VPC require the **peer to be in the same account** — you cannot enable them on a cross-account peered VPC
- Flow Logs are **all-or-nothing per ENI** with no inclusion/exclusion filters — log everything, then filter at the destination (CloudWatch Logs filter, Athena query). For packet-level filtering, use Network Firewall
- Existing flow logs **do not auto-upgrade** to newer field versions — to capture V7 ECS or V8 `reject-reason` fields, you must delete and recreate with a custom format
- `SKIPDATA` failures are **silent** — if the IAM role lacks `logs:CreateLogStream` / `logs:PutLogEvents`, records are dropped without a console error. Always validate the role's trust policy for `vpc-flow-logs.amazonaws.com`
- VPC-level Flow Logs log **every ENI in the VPC** — a busy multi-AZ VPC can generate TBs/month into CloudWatch Logs at $0.50/GB ingestion. For long-term retention, send to S3 in Parquet instead
- S3 delivery adds **~5 minutes of delay** on top of the aggregation interval — it is not just the 1/10-min aggregation window
- Each log type captures a **different layer** (Flow Logs, ELB/ALB access logs, CloudFront logs, WAF logs, CloudTrail) — don't pick Flow Logs when the question asks for HTTP request URIs, user agents, or response codes (those are ALB/CloudFront access logs)
- Flow Logs only see **TCP/UDP traffic** — EFA traffic over RDMA (HPC bypass paths) is not captured
